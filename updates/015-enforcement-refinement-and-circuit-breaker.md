# Обновление стандарта GO-BUILD: v1.14.1 — Enforcement Refinement & Watertight Circuit Breaker

**Дата**: 2026-09-09  
**Версия**: v1.14.1  
**Приоритет**: CRITICAL  
**Статус**: Активен  

---

## 1. Причина обновления

По результатам стресс-тестирования и второго аудита v1.14.0 было выявлено 8 критических уязвимостей (лазеек) в механизме принудительного исполнения:
1. **Tool Call Ghost Bypass**: возможность выполнения мутирующего tool call в обход текстовой проверки Pre-Action Gate.
2. **Ограничение Data-Flow**: определение Strict Technical Necessity блокировало передачу данных через пропсы/состояния при добавлении запрошенного элемента.
3. **Ложные срабатывания Circuit Breaker**: предохранитель аварийно блокировал обычные автоисправления синтаксиса или форматирования линтера.
4. **Конфликт Task Sizing**: шаблонные механические правки по нескольким файлам ошибочно классифицировались как `FULL_PROJECT`.
5. **Коллизия Модульности и Минимальности**: правило P1-10 провоцировало создание новых файлов в точечных задачах.
6. **Остаточные безусловные ловушки**: разделы 2, 3, 17 и финальные протоколы содержали старые формулировки об обязательном 16-блочном анализе для «любой» задачи.
7. **Лазейка общих рекомендаций UI/A11y**: разделы 4 и 6 использовались как повод для попутного рефакторинга.
8. **Отсутствие верстки в Pre-Action Gate**: версточные антипаттерны не отслеживались на этапе предварительного шлюза.

Релиз v1.14.1 устраняет все 8 уязвимостей, создавая герметичный контур дисциплины исполнения.

## 2. Ключевые архитектурные изменения v1.14.1

### 1. Защита от Tool Call Ghost Bypass (Pre-Action Audit Stamp)
Перед КАЖДЫМ вызовом мутирующего инструмента (`write_to_file`, `replace_file_content`, мутирующий `run_command`) агент обязан вывести в контекст стандартизированный штамп аудита:
```text
[PRE-ACTION AUDIT]: Scope: OK | Rules: P0,P1 | Checks: PASS | Decision: PASS
```
Вызов инструмента без предшествующего штампа считается грубым нарушением протокола P0-Violation.

### 2. Strict Technical Necessity & Data-Flow Plumbing
В категорию `[REQUIRED]` официально включена сквозная передача данных (Data-Flow & State Wiring):
* Если запрошенный UI-компонент требует данных, передача пропсов, подключение к существующему хуку/хранилищу или обновление контракта типов входят в `[REQUIRED]`.
* Спекулятивные UI-надстройки (диалоги, тосты, спиннеры, бейджи, если их не просили) остаются строго в `[FORBIDDEN]`.

### 3. Интеграция Layout Core 4 в Pre-Action Gate
Вопрос №3 Pre-Action Gate расширен до контроля базовых правил верстки:
* `Gap Before Margin`: отступы через gap, а не марджины.
* `Semantic First / No Div-Hell`: семантические теги вместо бессмысленных div.
* `No Positioning as Layout`: запрет absolute для базовой сетки.
* `Responsive Integrity`: сохранение целостности при сжатии окна.

### 4. Watertight Circuit Breaker
Предохранитель разделен на штатные и аварийные сценарии:
* **Штатные правки**: До 3 микро-исправлений синтаксиса, линтера или форматирования в рамках одного файла НЕ взводят Circuit Breaker.
* **Аварийные триггеры**: Scope Drift (переход к другим файлам при ошибке), Repeated Architectural Failure (повтор фундаментальной ошибки 2 раза), Scope Deadlock (тупик без расширения скоупа), Repeated Violation (повторный срыв P0/P1).

### 5. Mechanical Repetitive Changes в Task Sizing
В матрицу масштаба задач внедрено исключение для механических правок:
* Однотипная механическая замена (импорт, константа, версия API с diff ≤ 3–5 строк на файл) классифицируется как `SURGICAL_TASK` независимо от количества затронутых файлов.

### 6. Приоритет P1-3 над P1-10 для SURGICAL_TASK
Для точечных задач класса `SURGICAL_TASK` правило P1-3 (Хирургическая точность / Минимальные изменения) имеет строгий приоритет над P1-10 (Модульность). Выносить код в новые файлы или создавать модули ради абстракции запрещено.

### 7. Ликвидация старых требований 16-блочного анализа
Все разделы SKILL.md (Разделы 2, 3, 17, Протокол начала разработки, Обязательный формат результата анализа) приведены в строгое соответствие с Task Sizing:
* Для `SURGICAL_TASK` составление 16 блоков ТЗ категорически ЗАПРЕЩЕНО (действует фаст-трек).
* Для `MAJOR_FEATURE` выполняется сокращённый анализ (блоки 1, 6, 7, 11, 12).
* Для `FULL_PROJECT` обязателен полный 16-блочный анализ.

### 8. Приоритет P0 Scope Lock над рекомендациями Разделов 4 и 6
Общие рекомендации по чистоте кода, качеству верстки и accessibility (a11y) действуют строго в границах затронутых строк. Запрещено использовать их как оправдание попутного рефакторинга.
