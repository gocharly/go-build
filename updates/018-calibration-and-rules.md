# Обновление стандарта GO-BUILD: v1.16.1 — Калибровка и правила

**Дата**: 2026-09-10  
**Версия**: v1.16.1  
**Статус**: Активен  

---

## 1. Цель обновления

Закрепить результаты Adversarial Audit и Practical Benchmark для v1.15.0 и v1.16.0.
Устранить обнаруженные неоднозначности без добавления новых сложных систем контроля.
Перейти к спокойному, нейтральному и техническому стилю формулировок без маркетинговых и оценочных эпитетов.

## 2. Основные изменения и калибровки

### Модульность и простота кода
1. **Порог маленького модуля**: модуль размером примерно 30–50 строк или меньше с одним потребителем не выносится автоматически в отдельный файл. Логика остаётся локальной, если нет устойчивой границы, нескольких потребителей или явного требования архитектуры проекта.
2. **Запреты на искусственные структуры**: запрещено создавать `utils/` или `helpers/` ради одной функции, `services/` ради одного вызова, интерфейс ради одной реализации, фабрику ради одного объекта, DTO/wrapper только ради формальности.
3. **Принцип основного файла**: последовательный поток сценария (`get data → validate → transform → save → return`) сохраняется рядом, если вынос не даёт реального преимущества. Искусственные многослойные цепочки запрещены.
4. **Правило трёх (Rule of Three)**: конкретная реализация пишется первой; абстракция создаётся только при реальном повторном использовании (3-й случай) или явной архитектурной необходимости.
5. **Тест старшего инженера и проверка простоты (Simplicity Test)**: применяется к алгоритмической, преобразовательной и процедурной логике (сокращение 120 → 40–50 строк без потери читаемости). Правило не означает сокращение любой ценой и не применяется для разрушения established architecture фреймворка.
6. **Приоритет существующей архитектуры проекта**:
   ```text
   P0 Scope / User Request
   ↓
   Existing Project Architecture
   ↓
   Framework Conventions
   ↓
   Simplicity / Modularity
   ↓
   Optional Abstractions
   ```
7. **Универсальность языков**: правила модульности применяются независимо от языка с использованием нативных механизмов (Go packages, Rust modules/crates, TS/JS ESM, Python packages, Java, C#, C/C++, Swift, PHP).
8. **God File / God Module**: декомпозиция проводится только по независимым ответственностям, а не дроблением на 15 файлов по 10 строк.
9. **Простота функций**: отказ от механического правила «функция ≤ 20 строк». Главный критерий — понятность и отсутствие смешения ответственностей.

### Дисциплина интерфейса и верстки
1. **Subtle Border Fallback**: если элемент и родитель имеют одинаковый фон и разделение невозможно через отступы или цвет, разрешена минимальная рамка (`border: 1px solid var(--border-subtle)`).
2. **Visual Hierarchy Order**: перед рамкой последовательно проверяются отступы (spacing) → типографика → контраст → выравнивание → фон → рамка/тень.
3. **Accessibility Without Scope Expansion**: доступность учитывается в рамках изменяемого элемента, но не используется как повод для выхода за Scope Lock или рефакторинга соседнего кода.
4. **Responsive Integrity & Restructuring**: обязательная проверка диапазонов (320px–1440px+), безопасная работа с текстом во flex (`min-width: 0`, перенос/многоточие по контексту), перестройка desktop-структуры в вертикальный стек на мобильных экранах.
5. **Точечные задачи (Surgical Tasks)**: минимальный diff имеет безусловный приоритет; legacy-код не рефакторится «заодно».
6. **Data-Flow & State Wiring**: разрешено подключение существующих props, types, hooks, store, handlers без создания спекулятивной инфраструктуры (лишних toasts, modals, loaders).

### Стиль документации
* Исключены рекламные, пафосные и оценочные слова.
* Заголовки и текст приведены к нейтральному, спокойному техническому тону.
