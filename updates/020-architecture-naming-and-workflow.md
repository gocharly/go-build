## 1. Причина обновления

Закрепление стандартов прозрачной архитектуры, понятного именования сущностей по их действию и сквозного 24-шагового алгоритма разработки.

Архитектура проекта обязана сама объяснять код человеку без необходимости открывать каждый файл и изучать детали реализации.

---

## 2. Основные положения обновления

### 1. Нормативный справочник (`references/architecture-naming-and-workflow.md`)
Включает две части:
* **Часть 1. Архитектура проекта и именование (24 правила)**:
  - Структура отражает ответственность, а не техническую свалку файлов.
  - API изолировано от внутренней логики, модули группируются по домену.
  - Название файла отвечает на вопрос «Что внутри?» (`slugify.ts`, `password_hash.go`).
  - Функции называются строго по выполняемому действию (`calculatePrice`, `createUser`), запрет абстрактных названий (`doSomething`, `process`, `handle`, `helper`).
  - Предсказуемость терминологии (`createUser`/`getUser`, а не вперемешку с `makeUser`/`fetchUserData`).
  - Названия API точно описывают ресурс и HTTP-действие.
  - Направление зависимостей понятно (`API → Domain → Infrastructure`), запрет циклов.
  - Запрет папок ради одного файла и микрофайлов ради каждой мелкой функции.
  - Комментарии краткие, объясняют «зачем/почему», а не повторяют очевидный код.
* **Часть 2. Алгоритм разработки (24 шага)**:
  - Сквозной цикл: `Понять задачу → Изучить проект → Найти существующий код → Определить Scope → Найти правильное место → Определить архитектурную границу → Спроектировать имена → Спроектировать простой flow → Реализовать минимальное решение → Проверить архитектуру → Проверить UI/responsive → Запустить проверки → Проверить diff → Проверить Scope → Завершить`.
  - Защита чужого кода при точечных задачах (`SURGICAL_TASK`).
  - Поиск первопричины проблемы вместо маскирования новыми слоями абстракций.

### 2. Чеклист «Architecture & Naming Audit» в Разделе 16 (SKILL.md)
Добавлен блок 7 в приемочный аудит:
- [ ] Папки и модули отражают реальные домены/ответственности
- [ ] Файлы названы конкретно по назначению
- [ ] Функции названы по действию
- [ ] Одинаковые действия называются единообразно
- [ ] Названия API точно описывают ресурс и действие
- [ ] Публичный API модуля минимален
- [ ] Зависимости логичны и направлены, нет циклических зависимостей
- [ ] Комментарии короткие и полезные
