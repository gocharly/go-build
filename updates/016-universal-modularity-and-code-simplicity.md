# Обновление стандарта GO-BUILD: v1.15.0 — Universal Modular Architecture & Code Simplicity

**Дата**: 2026-09-09  
**Версия**: v1.15.0  
**Приоритет**: CRITICAL  
**Статус**: Активен  

---

## 1. Причина обновления

Предыдущие версии стандарта содержали базовые правила модульности, но они не давали универсальных, языково-агностичных предписаний для организации кода в разнородных стеках (Backend, Frontend, Fullstack, CLI, Desktop, Mobile, APIs, Scripts, Infrastructure, Data Processing) и не были защищены от двух крайностей:
1. **Антипаттерн свалки (God Module / Dump Folders)**: бесконтрольное появление каталогов `utils/`, `helpers/`, `common/`, `misc/`, объединяющих несвязанную логику;
2. **Избыточная фрагментация (Over-Modularization)**: дробление 100 строк читаемого кода на 8 микро-файлов с искусственными абстракциями ради соблюдения формальных лимитов строк.

Релиз v1.15.0 внедряет целостную **Универсальную модульную архитектуру и дисциплину простоты кода (Universal Modular Architecture & Code Simplicity)**.

---

## 2. Ключевые архитектурные компоненты v1.15.0

### 1. Доменная модульность (Responsibility-Based Modules)
Код группируется по единой доменной ответственности (`auth/`, `payments/`, `users/`, `storage/`), а не по техническим типам (`controllers/`, `models/`, `helpers/`). Модуль объединяет функции, типы, валидаторы, сервисы и хуки, если они обслуживают одну задачу.

### 2. Нативные системы модулей (Native Module System)
Категорический запрет навязывать структуру Go проектам на других языках. Использование нативных механизмов: Go packages, Rust modules/crates, Python packages, TypeScript ES modules/feature folders, Java packages, C# namespaces, C/C++ headers/modules, Swift SPM, PHP namespaces.

### 3. Принцип основного файла (Main File Principle)
Входные файлы (`main.go`, `index.ts`, `app.py`, экранные контейнеры) описывают высокоуровневый поток выполнения (Control Flow: получить входные данные → вызвать модуль → обработать → вернуть), а не содержат сотни строк монолитной логики.

### 4. Регламент и 5 вопросов выноса (Module Extraction Gate)
Вынос кода в модуль разрешен только при наличии самостоятельной ответственности, замкнутой логики или реального повторного использования. Перед выносом агент отвечает на 5 бинарных вопросов. Главный критерий: **код обязан стать проще для понимания**.

### 5. Запрет избыточной модульности и фрагментации (Do Not Over-Modularize)
Запрещено выносить код ради уменьшения строк, красивого дерева папок или двухстрочной логики. Одноразовый код остаётся по месту. Запрещены механические лимиты строк («функция ≤ 20 строк»).

### 6. Приоритет минимальности в SURGICAL_TASK
Для точечных задач подтверждён абсолютный приоритет: `P1-3 (Surgical Precision) > P1-10 (Universal Modularity)`. Запрещено создавать новые модули или абстракции, если задача решается локальной правкой.

### 7. Повторное использование без спекулятивных абстракций
Правило трёх шагов: 1-й случай — конкретная реализация; 2-й случай — оценка совпадения; 3-й случай — общий модуль. Запрещены абстракции «на будущее» и убер-классы (`BaseManager`, `GenericHelper`, `UniversalUtils`).

### 8. 7 контрольных вопросов простоты и Senior Simplicity
Перед финализацией задачи агент задаёт 7 контрольных вопросов упрощения (удаление лишнего кода, устранение лишних слоев, спрямление control flow).

### 9. Детекция God File & God Module
Разделение файлов и модулей с разнородными доменными областями по естественным границам.

### 10. Минимальная поверхность API и запрет циклов
Small Public API + Private Implementation. Запрет циклических зависимостей (`A → B → C → A`).
