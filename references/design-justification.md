# GO-BUILD: Design Justification — Обоснование каждого визуального решения

## Основной принцип

GO-BUILD запрещено добавлять визуальные элементы только потому, что:
* так красивее;
* так выглядит современнее;
* так выглядит премиальнее;
* так страница кажется менее пустой;
* так принято в других дизайнах;
* элемент был автоматически предложен библиотекой;
* агент считает, что интерфейсу «чего-то не хватает».

Каждый элемент интерфейса должен иметь конкретную причину существования.
Если причина отсутствует — элемент не создаётся.

---

# Visual Purpose Gate

Перед добавлением нового визуального элемента GO-BUILD обязан определить его назначение.

Каждый элемент должен относиться минимум к одной из следующих категорий:

### 1. ДЕЙСТВИЕ
Элемент позволяет пользователю выполнить конкретное действие.
Примеры:
* кнопка;
* поле ввода;
* переключатель;
* меню;
* ссылка;
* элемент управления.

---

### 2. НАВИГАЦИЯ
Элемент помогает пользователю понять:
* где он находится;
* куда может перейти;
* как вернуться назад;
* какие разделы доступны.

---

### 3. РЕАЛЬНАЯ ИНФОРМАЦИЯ
Элемент отображает данные, необходимые пользователю.
Например:
* баланс;
* заказ;
* статус доставки;
* дата;
* уведомление;
* данные аккаунта.

Информация должна быть:
* реальной;
* контекстной;
* необходимой.

---

### 4. ВИЗУАЛЬНАЯ ИЕРАРХИЯ
Элемент помогает пользователю быстрее понимать структуру страницы.
Например:
* заголовок;
* подзаголовок;
* разделение функциональных областей;
* группировка связанных элементов.

Визуальная иерархия не означает автоматическое создание:
* карточек;
* рамок;
* декоративных контейнеров;
* бейджей.

---

### 5. ОБРАТНАЯ СВЯЗЬ
Элемент сообщает пользователю результат его действия.
Например:
* загрузка (loading state / skeleton);
* успешное сохранение;
* ошибка;
* изменение состояния;
* подтверждение действия.

---

# Если элемент не проходит Visual Purpose Gate

Если визуальный элемент:
* не выполняет действие;
* не помогает навигации;
* не передаёт необходимую информацию;
* не создаёт необходимую иерархию;
* не предоставляет обратную связь;

его создание запрещено.

**Элемент удаляется до начала реализации.**

---

# Запрет на Filling Empty Space

Пустое пространство не является ошибкой.

Запрещается автоматически добавлять элементы только потому, что:
* страница выглядит пустой;
* между блоками много пространства;
* контейнер кажется слишком большим;
* header кажется недостаточно заполненным;
* hero выглядит минималистично.

### Запрещённая логика:
> «Здесь слишком пусто, давайте добавим карточки.»  
> «Добавим небольшой статус.»  
> «Добавим иконку.»  
> «Добавим подпись.»  
> «Добавим бейдж.»  
> «Добавим несколько цифр.»  

### Правильный вопрос:
**Действительно ли пользователю не хватает информации или агенту просто визуально непривычно видеть свободное пространство?**

Свободное пространство разрешено использовать как полноценный инструмент визуальной иерархии.

---

# No Decoration Without Purpose

Декоративный элемент запрещён, если он не выполняет конкретную функцию.

Это относится к:
* иконкам;
* точкам;
* линиям;
* рамкам;
* бейджам;
* цветным блокам;
* контейнерам;
* абстрактным фигурам;
* декоративным текстам.

Перед созданием необходимо ответить:
```text
Что делает этот элемент?
Какую проблему пользователя он решает?
Что изменится, если его удалить?
```

Если ответы:
```text
Ничего не делает.
Никакую проблему не решает.
Ничего не изменится.
```
элемент запрещён.

---

# Design Justification Rule

Нельзя использовать аргумент:

**«Это улучшает дизайн».**

Это не является достаточным обоснованием. Необходимо объяснить:

```text
Как именно этот элемент улучшает:
- понимание интерфейса;
- скорость выполнения задачи;
- навигацию;
- восприятие информации;
- визуальную иерархию.
```

Если конкретного объяснения нет — элемент не добавляется.

---

# Component Justification

Использование готового компонента из библиотеки также требует обоснования.
Нельзя автоматически использовать компонент только потому, что он существует.

Например:
* Card;
* Badge;
* Tooltip;
* Popover;
* Separator;
* Alert;
* Tabs.

Перед использованием необходимо определить:
```text
Какую задачу решает этот компонент?
Почему обычная структура страницы не подходит?
Почему именно этот компонент улучшает UX?
```

Если компонент не нужен — не использовать его.

**Наличие компонента в shadcn/ui или другой библиотеке не является причиной добавлять его в интерфейс.**

---

# Content Justification

Каждый текстовый элемент должен иметь конкретную цель.

Перед добавлением текста необходимо определить:
```text
Что пользователь узнаёт из этого текста?
Нужно ли ему это знать сейчас?
Меняет ли эта информация его действие или понимание страницы?
```

Если текст:
* ничего не объясняет;
* не помогает действию;
* не передаёт информацию;
* существует ради дизайна;

его запрещено добавлять.

---

# Icon Justification

Перед добавлением иконки необходимо определить:
```text
Заменяет ли иконка текст?
Помогает ли она быстрее распознать действие?
Нужна ли она пользователю?
Будет ли интерфейс хуже без неё?
```

Если нет — иконка не добавляется.

Запрещается автоматически добавлять иконки:
* перед заголовками;
* рядом с обычным текстом;
* в каждой карточке;
* в каждом разделе;
* исключительно ради визуального разнообразия.

---

# Container Justification

Каждый контейнер должен иметь конкретную структурную или функциональную причину.

Перед созданием контейнера необходимо проверить:
```text
Объединяет ли он связанные элементы?
Нужно ли визуально отделить эту область?
Есть ли внутри самостоятельная функциональная группа?
Можно ли решить задачу без контейнера?
```

Если контейнер не нужен — его запрещено создавать.

Особенно запрещается:
```text
Container
└── Container
    └── Container
        └── Content
```
без функционального или структурного основания.

---

# Default to Less

При наличии двух решений:

### Решение A
Добавить:
* контейнер;
* иконку;
* подпись;
* статус;
* декоративный элемент.

### Решение B
Не добавлять ничего лишнего.

По умолчанию GO-BUILD обязан выбирать:

**Решение B.**

Дополнительный элемент добавляется только после прохождения Design Justification.

---

# Removal Test

После создания интерфейса GO-BUILD обязан провести обратную проверку.

Для каждого второстепенного элемента задать вопрос:

**Что произойдёт, если удалить этот элемент?**

Возможные результаты:
1. **Интерфейс стал хуже**: элемент может быть оправдан.
2. **Ничего не изменилось**: элемент необходимо удалить.
3. **Интерфейс стал лучше**: элемент необходимо удалить немедленно.

---

# Design Justification Final Check

Перед сдачей frontend-интерфейса необходимо проверить:

```text
[ ] 1.  Каждый элемент выполняет конкретную функцию.
[ ] 2.  Нет элементов, добавленных только ради красоты.
[ ] 3.  Нет элементов, добавленных для заполнения пустого пространства.
[ ] 4.  Каждый текст передаёт необходимую информацию.
[ ] 5.  Каждая иконка имеет конкретное назначение.
[ ] 6.  Каждый контейнер имеет структурную или функциональную причину.
[ ] 7.  Нет компонентов, добавленных только потому, что они доступны в библиотеке.
[ ] 8.  Нет декоративных статусов.
[ ] 9.  Нет бессмысленных подписей.
[ ] 10. Нет искусственного визуального разнообразия.
[ ] 11. Свободное пространство не заполнено искусственными элементами.
[ ] 12. Каждый второстепенный элемент прошёл Removal Test.
[ ] 13. При возможности выбран более простой интерфейс.
[ ] 14. Интерфейс построен вокруг задачи пользователя, а не вокруг желания сделать дизайн визуально сложнее.
```

---

# Ключевой принцип

GO-BUILD никогда не должен принимать решение:

**«Добавим это, потому что так будет красивее».**

Вместо этого необходимо определить:

**«Какую конкретную пользу этот элемент принесёт пользователю?»**

Если конкретной пользы нет — элемента не должно существовать.

---

# Финальное правило

Хороший интерфейс определяется не количеством добавленных элементов.

Хороший интерфейс определяется количеством ненужных элементов, которые были сознательно не добавлены.

* **Когда есть сомнение — не добавляй.**
* **Когда элемент нельзя обосновать — удаляй.**
* **Когда интерфейс работает без элемента — не создавай элемент.**
