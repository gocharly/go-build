# Modularity & Code Simplicity

**Версия стандарта**: v1.16.1  
**Статус**: Обязательный стандарт (P1-MANDATORY)  
**Область действия**: Все языки программирования, фреймворки и типы проектов (Backend, Frontend, Fullstack, CLI, Desktop, Mobile, Libraries, APIs, Services, Scripts, Infrastructure, Data Processing).

---

## 1. Universal Modularity

Модульность обязательна только тогда, когда она реально улучшает структуру проекта.

### Правило

Не создавать отдельный файл или модуль только потому, что логика имеет отдельную смысловую ответственность.

Перед созданием модуля проверить:
1. Есть ли реальная самостоятельная ответственность?
2. Есть ли естественная граница зависимости?
3. Используется ли логика в нескольких местах?
4. Стала ли локальная реализация существенно сложной?
5. Соответствует ли вынос существующей архитектуре проекта?

Если ответы отрицательные — оставить код локально.

### Маленький модуль

Модуль размером примерно 30–50 строк или меньше с одним потребителем **не должен автоматически выноситься**.

Но это не является абсолютным запретом. Вынос маленького модуля допустим, если:
* он имеет самостоятельную ответственность;
* имеет естественную архитектурную границу;
* используется или очевидно предназначен для реального повторного использования;
* этого требует существующая архитектура проекта;
* локальное размещение делает основной модуль существенно хуже.

### Запрещено создавать

* `utils/` ради одной функции;
* `helpers/` ради одной функции;
* `services/` ради одного вызова;
* интерфейс ради одной реализации;
* фабрику ради одного объекта;
* DTO или Wrapper только ради формальности;
* отдельный файл только ради уменьшения количества строк.

## 2. Main File Principle

Основной файл должен оставаться центром конкретного сценария, если вынос не даёт реального преимущества.

Пример:
```text
get data
→ validate
→ transform
→ save
→ return
```

Если вся логика короткая, понятная и используется только здесь — она остаётся рядом.

Не создавать искусственную архитектуру:
```text
controller
→ service
→ helper
→ factory
→ validator
→ mapper
→ repository
```
если задача не требует такого разделения.

---

## 3. Rule of Three

Не создавать абстракцию для предполагаемого будущего использования.

Сначала конкретная реализация.

Абстракция появляется при:
* реальном повторном использовании;
* нескольких одинаковых сценариях (3-й случай);
* устойчивой общей логике;
* необходимости независимой замены реализации;
* явном требовании архитектуры проекта.

Не проектировать API для воображаемого будущего.

---

## 4. Тест старшего инженера и проверка простоты (Simplicity Test)

### Правило

> Если сложную алгоритмическую, преобразовательную или процедурную логику можно сделать значительно короче без потери поведения, читаемости и архитектурной совместимости — упростить её.

Например:
```text
120 строк → 40–50 строк
```
если это действительно возможно.

Но правило **не означает**:
```text
200 строк → обязательно 50 строк любой ценой
```

### Не сокращать код, если это:
* ломает установленную архитектуру проекта;
* уничтожает естественные границы framework;
* ухудшает читаемость;
* объединяет независимые ответственности;
* нарушает существующие project conventions;
* усложняет тестирование;
* создаёт скрытые зависимости.

## 5. Existing Project Architecture

В существующем проекте сначала соблюдать его реальные архитектурные соглашения.

Например, если проект использует:
```text
Controller
Service
Repository
DTO
```
не объединять всё в один файл только ради уменьшения количества строк.

Принцип простоты применяется прежде всего к внутренней логике этих компонентов.

Упрощать:
```text
сложный алгоритм → простой алгоритм
```
а не:
```text
установленная архитектура → уничтожение архитектуры
```

### Приоритет

```text
P0 Scope / User Request
↓
Existing Project Architecture
↓
Framework Conventions
↓
Simplicity / Modularity
↓
Optional Abstractions
```

## 6. Universal Language Rule

Все правила модульности применяются независимо от языка.

Не привязывать архитектурные правила к Go. Использовать нативную систему конкретного языка:

| Язык / Платформа | Нативный механизм модульности | Практика применения |
|---|---|---|
| **Go** | `packages`, `internal/` | Пакеты по доменам (`auth`, `payments`), избегать общих `pkg/utils`, идиоматичный `internal/`. |
| **Rust** | `modules`, `crates` | Иерархия `mod`, инкапсуляция через `pub(crate)` / `pub`, четкие границы. |
| **TypeScript / JS** | `ES Modules`, feature-folders | Feature-based модули (`features/auth`), explicit named exports, изоляция через `index.ts`. |
| **Python** | `packages` (`__init__.py`), `modules` | Доменные пакеты, явные контракты импортов, отсутствие циклических зависимостей. |
| **Java / Kotlin** | `packages` | Пакеты по фичам, package-private видимость для сокрытия реализации. |
| **C# (.NET)** | `namespaces`, projects | Namespaces по доменам, использование `internal`. |
| **C / C++** | `headers`, source, C++20 modules | Изоляция в заголовках, реализация в source, разделение по функционалу. |
| **Swift** | `modules`, Swift Packages (SPM) | Модули по фичам, `internal` по умолчанию, `public` только для интерфейса. |
| **PHP** | `namespaces` (PSR-4), composer | Domain-driven структура, PSR-4 неймспейсы, сокрытие деталей. |

Не создавать искусственные архитектурные слои, если язык и проект этого не требуют.

## 7. God File / God Module

Большой файл не нужно автоматически разбивать.

Сначала определить, почему он большой.

Разделять только независимые ответственности.

* **Неудачный рефакторинг**:
  ```text
  file.ts → 15 файлов по 10 строк
  ```
* **Обоснованный рефакторинг**:
  ```text
  feature/
  ├── main flow
  ├── independent domain logic
  └── independent infrastructure logic
  ```

Каждый новый модуль должен иметь понятную причину существования.

---

## 8. Function Simplicity

Функция должна иметь понятную основную ответственность.

Не применять искусственное правило «функция ≤ 20 строк». 20 строк — не магическое число.

Если функция 60 строк является простой, последовательной и понятной — не разбивать её искусственно.

Если функция 15 строк содержит несколько независимых сложных ответственностей — её можно разделить.

### Цель

Не минимальное количество строк. Цель:
```text
минимум необходимой сложности + максимум читаемости
```

---

## 9. Small Public API & Direction of Dependencies

* **Small Public API + Private Implementation**: модуль экспортирует наружу только необходимый контракт. Внутренняя реализация сокрыта.
* **Направление зависимостей**: запрещены циклические зависимости (`A → B → C → A`). Зависимости направлены сверху вниз или от деталей к абстракциям.
* Не навязывать многослойную архитектуру компактным скриптам и утилитам.

---

## 10. Refactoring Safety

При проведении рефакторинга:
1. Внешнее поведение и контракты API сохраняются неизменными.
2. Изменения строго ограничены рамками Scope Lock.
3. Каждый шаг проверяется по формуле `Step → Verify`.

---

## 11. Surgical Task Override

Для точечных задач (`SURGICAL_TASK`):
* минимальный diff имеет приоритет;
* не применять полный архитектурный рефакторинг;
* не создавать новые модули без необходимости;
* не исправлять несвязанный код.

Правило минимальности имеет приоритет над правилом модульности:
```text
P1-3 Surgical Precision  >>>  P1-10 Universal Modularity
```

---

## 12. Основной принцип

GO-BUILD не должен писать максимально много кода.  
GO-BUILD не должен создавать максимально много файлов.  
GO-BUILD не должен рефакторить всё вокруг задачи.  

GO-BUILD должен создавать:
```text
минимально необходимый код
+ понятную структуру
+ нативную архитектуру проекта
+ минимально необходимую абстракцию
```

Главный вопрос перед любым усложнением:
> «Это действительно необходимо для текущей задачи или я создаю сложность на будущее?»  
> Если второе — не делать.
