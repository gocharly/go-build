# GO-BUILD: Архитектура проекта, именование и алгоритм разработки

## Часть 1. Архитектура проекта и именование

### 1. Общий принцип
Архитектура проекта должна быть понятной человеку, который впервые открыл проект.

По структуре проекта должно быть максимально легко определить:
* где находится API;
* где находится бизнес-логика;
* где находятся модули;
* где находятся модели и типы;
* где работа с базой данных;
* где внешние интеграции;
* где находятся UI-компоненты;
* где находятся утилиты;
* где находится основной flow конкретной функции.

Не создавать структуру только ради формального разделения файлов.
Каждая папка, модуль и файл должны иметь понятную причину существования.

---

### 2. Структура должна отражать ответственность
Организовывать код по смыслу и ответственности, а не случайным образом.

**Плохо:**
```text
src/
├── misc/
├── stuff/
├── helpers/
├── common/
├── utils/
└── random/
```

**Хорошо:**
```text
src/
├── api/
├── auth/
├── users/
├── payments/
├── notifications/
└── database/
```
Название должно объяснять содержимое без необходимости открывать каждый файл.

---

### 3. API должно быть отделено от внутренней логики
Если проект содержит API, его структура должна быть очевидной.

Например:
```text
api/
├── users/
├── auth/
└── payments/
```

Внутри конкретного домена:
```text
users/
├── user.go
├── user_service.go
├── user_repository.go
└── user_api.go
```
Но создавать все эти файлы автоматически запрещено. Файл создаётся только тогда, когда соответствующая ответственность действительно существует.

---

### 4. Модули группируются по домену
Если несколько файлов относятся к одной функциональности, они должны находиться рядом.

Например:
```text
users/
├── user.go
├── user_service.go
├── user_repository.go
└── user_api.go
```
а не:
```text
models/
└── user.go
services/
└── user_service.go
repositories/
└── user_repository.go
api/
└── user_api.go
```
если первая структура лучше отражает конкретный проект и его функциональные границы. Не применять один шаблон ко всем проектам механически.

---

### 5. Файл должен описывать своё назначение
Название файла должно отвечать на вопрос:
> «Что находится внутри этого файла?»

**Плохо:** `helpers.ts`, `common.ts`, `misc.go`, `stuff.py`, `manager.rs`, `base.ts`, `data.go`, `utils.ts` (если из названия невозможно определить назначение).

**Хорошо:** `slugify.ts`, `password_hash.go`, `payment_client.ts`, `user_repository.go`, `invoice_parser.py`, `notification_sender.ts`.

Название должно быть конкретным.

---

### 6. Функция должна называться по выполняемому действию
Название функции должно объяснять, что она делает:
* `calculatePrice()` — считает стоимость
* `calculateTax()` — считает налог
* `createUser()` — создаёт пользователя
* `validateEmail()` — проверяет email
* `slugifyTitle()` — преобразует заголовок в slug

Не использовать бессмысленные названия: `doSomething()`, `process()`, `handle()`, `run()`, `execute()`, `manage()`, `helper()`, если название не объясняет конкретную операцию.

---

### 7. Название должно соответствовать реальной ответственности
Не называть функцию `calculatePrice`, если она одновременно:
* получает данные из БД;
* отправляет HTTP-запрос;
* создаёт пользователя;
* считает цену;
* сохраняет результат.

В таком случае ответственность должна быть разделена настолько, насколько это действительно необходимо. Название должно соответствовать реальному поведению.

---

### 8. Имена должны быть предсказуемыми
Если в проекте используется:
```text
createUser, getUser, updateUser, deleteUser
```
не создавать рядом:
```text
makeUser, fetchUserData, modifyUser, removeUserRecord
```
для тех же операций без причины. Использовать последовательную терминологию. Одинаковые действия должны называться одинаково по всему проекту.

---

### 9. Названия API должны описывать ресурс и действие
API endpoints, handlers, controllers и связанные функции должны использовать понятные имена:
```text
GET    /users       → getUsers
GET    /users/:id   → getUser
POST   /users       → createUser
PATCH  /users/:id   → updateUser
DELETE /users/:id   → deleteUser
```
Не использовать абстрактные `handleRequest`, `processData`, `executeAction`, `mainHandler`, если можно точно описать операцию.

---

### 10. Модуль должен иметь ограниченную ответственность
Модуль не должен становиться контейнером для несвязанных функций.
Не создавать свалку `utils/` с вызовами цен, email, дат и юзеров.
Группировать по доменам: `pricing/`, `email/`, `users/`. При этом не создавать отдельную папку для каждой функции автоматически.

---

### 11. API модулей должно быть маленьким и понятным
Каждый модуль наружу предоставляет только то, что действительно нужно другим частям проекта (`Small Public API + Private Implementation`). Не экспортировать всё подряд.

---

### 12. Внутренние детали не должны становиться публичным API
Если функция используется только внутри модуля, не делать её публичной только для удобства. Сначала `private/local`, и только при реальной необходимости — `public/exported`.

---

### 13. Направление зависимостей должно быть понятным
Не создавать хаотические зависимости (`A → B → C → A`). Направление зависимостей должно быть логичным для выбранной архитектуры:
```text
API → Application / Domain → Infrastructure
```

---

### 14. Не создавать циклические зависимости
Не допускать циклов между модулями (`users ↔ payments`). При необходимости вынести общую концепцию в подходящее место, а не создавать случайный `common` или `utils`.

---

### 15. Не создавать папки ради одного файла
Не создавать `calculator/calculator.ts`, если проект не получает от этого архитектурного преимущества. Папка создаётся, когда появляется реальная группа связанных компонентов.

---

### 16. Не создавать файл ради каждой функции
Не дробить мелкие функции одного сценария на `calculate_price.ts`, `validate_price.ts`, `format_price.ts`. Объединять в локальный файл `pricing.ts`.

---

### 17. Не создавать огромные файлы
Если файл начинает содержать несколько самостоятельных подсистем, его необходимо разделить по доменным ответственностям, связанности и читаемости (а не чисто по числу строк).

---

### 18. Комментарии
Комментарии использовать там, где код сам по себе не объясняет важную причину или поведение.
* Хорошо: `// Используем UTC, чтобы дата не зависела от часового пояса пользователя.`
* Плохо: `// Устанавливаем дату`

---

### 19. Комментарии должны быть короткими
Объяснять: зачем это сделано, почему выбран такой способ, какое неочевидное поведение нужно сохранить. Не писать длинные объяснения очевидного кода.

---

### 20. Названия важнее комментариев
Сначала сделать код понятным через структуру, названия, небольшие функции и понятные зависимости. Комментарии не заменяют плохое именование.

---

### 21. README и документация
Если архитектура проекта достаточно сложная, добавить короткое описание структуры папок и назначений модулей в README.

---

### 22. Архитектурная проверка перед созданием нового файла
1. Какую конкретную ответственность он получает?
2. Почему эта ответственность должна быть отдельно?
3. Кто будет его использовать?
4. Почему существующий файл уже не подходит?
5. Как будет называться файл?
6. Можно ли понять его назначение только по названию?

---

### 23. Архитектурная проверка после изменения
* [ ] Структура понятна без глубокого изучения кода
* [ ] Папки отражают реальные домены/ответственности
* [ ] Названия файлов описывают их назначение
* [ ] Названия функций описывают их действие
* [ ] Названия API понятны
* [ ] Нет бессмысленных utils/common/misc файлов
* [ ] Нет ненужных маленьких модулей
* [ ] Нет функций, вынесенных только ради уменьшения строк
* [ ] Нет лишних public/exported функций
* [ ] Зависимости имеют понятное направление
* [ ] Нет новых циклических зависимостей
* [ ] Комментарии короткие и действительно полезные
* [ ] Existing project conventions сохранены

---

### 24. Главный принцип
Архитектура должна объяснять код сама:
```text
папка → файл → название функции → название модуля → направление зависимости
```

---

## Часть 2. Алгоритм разработки

### 1. Понять задачу
Определить: что именно нужно сделать, ожидаемый результат, связанные файлы, что менять нельзя. Сначала понять существующий код и структуру.

### 2. Изучить существующий проект
Схема проверки:
```text
структура проекта → соответствующий модуль → связанные файлы → существующие функции → существующие типы → существующие API → существующие зависимости → существующие UI-паттерны
```
Не создавать новую реализацию, если подходящая уже существует. Не дублировать логику.

### 3. Найти правильное место для изменения
Изменение размещается там, где находится его ответственность. Проверить возможность реализации в существующем модуле.

### 4. Определить масштаб задачи
* `SURGICAL_TASK`: точечное изменение, минимальный diff.
* `MAJOR_FEATURE`: изменение одной функциональности/экрана, несколько связанных модулей.
* `FULL_PROJECT`: новая система или проект с нуля; проектирование структуры и зависимостей до кода.

### 5. Зафиксировать Scope
`REQUESTED` (запрос), `PROTECTED` (нельзя трогать), `REQUIRED` (необходимо для работы), `FORBIDDEN` (запрещено добавлять).

### 6. Найти существующие точки расширения
Сначала использовать существующие функции, хуки, компоненты, сервисы, репозитории. Новый код создавать только при недостаточности имеющегося.

### 7. Спроектировать решение
Минимальный путь: `input → existing API/module → required logic → output`. Без спекулятивных слоев и будущих настроек.

### 8. Определить архитектурную границу
Приоритет:
```text
локальная реализация ↓ существующий модуль ↓ новый модуль
```

### 9. Спроектировать имена
Подобрать понятные имена до написания сущностей. Никаких абстрактных `helper`, `manager`, `temp`, `data`.

### 10. Реализовать минимальное решение
Писать только код, необходимый для задачи. Ничего «на всякий случай» или «на будущее».

### 11. Сначала простое решение
Простая функция и прямой вызов вместо многослойных абстракций (`interface → implementation → factory → wrapper → service`).

### 12. Не усложнять код искусственно
Не разбивать функцию ради строк и не создавать модули ради красивого дерева.

### 13. Проверять архитектуру во время разработки
Контролировать место размещения кода, появление зависимостей и понятность имен на каждом шаге.

### 14. Держать зависимости понятными
Исключать циклические и запутанные перекрестные зависимости.

### 15. Реализовывать UI через структуру, а не позиционирование
Основной layout: `flex`, `grid`, `normal flow`, `gap`, `padding`. Никакого обычного лейаута через `absolute`.

### 16. UI сначала сделать структурно правильным
Сначала семантика, контейнеры, сетка, responsive. Затем типографика и цвета. Border и shadow — в последнюю очередь (Border Last).

### 17. Responsive проверять во время реализации
Тестировать от 320px до 1440px+ (длинный текст, переполнение, сжатие flex/grid).

### 18. Не исправлять чужой код без необходимости
При точечных правках (`SURGICAL_TASK`) не трогать соседний legacy-код и чужую верстку.

### 19. Проверить результат (Код, Архитектура, UI)
Сверить результат по контрольным чек-листам кода, архитектуры и вёрстки.

### 20. Запустить доступные проверки
Использовать проектные тесты, линтеры, проверку типов и сборку.

### 21. Проверить diff
Убедиться, что каждая строка в diff прямо следует из запроса.

### 22. Финальная проверка Scope
`REQUESTED` выполнено, `PROTECTED` не затронуто, `FORBIDDEN` не добавлено.

### 23. Если обнаружена проблема
Искать первопричину и самое простое исправление (`problem → cause → simplest fix → verify`). Не маскировать проблему новыми абстракциями.

### 24. Итоговый принцип разработки
```text
Понять задачу → Изучить проект → Найти существующий код → Определить Scope → Найти правильное место → Определить архитектурную границу → Спроектировать имена → Спроектировать простой flow → Реализовать минимальное решение → Проверить архитектуру → Проверить UI/responsive → Запустить проверки → Проверить diff → Проверить Scope → Завершить
```
