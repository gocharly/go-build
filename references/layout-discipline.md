# GO-BUILD: Layout & Markup Discipline — Дисциплина верстки и разметки

## Основная цель

GO-BUILD должен создавать чистую, логичную и структурированную вёрстку.

Интерфейс должен строиться не путём случайного добавления контейнеров, а через правильную структуру документа, логические группы элементов и подходящие инструменты layout.

Каждый элемент в DOM должен иметь понятную причину существования.

### Главный принцип

**Сначала правильная структура. Потом layout. Потом визуальное оформление.**

*(Не наоборот).*

---

# 1. Semantic First

Перед использованием обычного `div` необходимо определить, существует ли подходящий семантический HTML-элемент.

Использовать по назначению:
* `header`;
* `nav`;
* `main`;
* `section`;
* `article`;
* `aside`;
* `footer`;
* `form`;
* `button`;
* `label`;
* `input`;
* `table`;
* `ul`;
* `ol`;
* `li`.

Не использовать `div` для всего подряд.

### Запрещённый подход:
```html
<div>
  <div>
    <div>
      <div>Dashboard</div>
    </div>
  </div>
</div>
```

Правильная структура должна отражать реальное назначение содержимого.

---

# 2. No DIV for No Reason

Каждый дополнительный контейнер должен иметь конкретную техническую или структурную причину.

Дополнительный wrapper разрешается создавать только если он необходим для:
* layout;
* группировки связанных элементов;
* positioning;
* overflow;
* animation;
* отдельного функционального состояния;
* accessibility;
* логического разделения интерфейса.

Если контейнер не выполняет ни одну из этих задач — он запрещён.

Перед добавлением wrapper необходимо спросить:
```text
Зачем нужен этот контейнер?
Какую задачу он решает?
Можно ли добиться того же результата без него?
```

---

# 3. Structure Before Styling

Запрещается сначала создавать большое количество `div`, а затем пытаться сделать из них интерфейс через CSS.

Правильный порядок:
1. Определить структуру страницы.
2. Определить семантические области.
3. Определить логические группы элементов.
4. Выбрать инструмент layout (flex / grid).
5. Применить визуальные стили (typography, spacing, colors).

---

# 4. Flex vs Grid

## Использовать FLEX, когда:
* элементы выстраиваются в одном направлении (горизонтально или вертикально);
* необходимо распределить пространство между элементами в строке/колонке;
* создаётся header, navbar, список тегов, строка кнопок;
* размер элементов зависит от их контента.

Примеры:
* навигационная панель;
* группа кнопок;
* карточка с заголовком, текстом и кнопкой;
* вертикальный список.

---

## Использовать GRID, когда:
* присутствуют строки и колонки одновременно;
* необходима двухмерная структура;
* требуется стабильная сетка;
* несколько элементов должны занимать определённые области;
* создаётся dashboard;
* создаётся сложный responsive layout.

Примеры:
* dashboard layout;
* data overview;
* cards grid;
* forms;
* complex application layout.

---

## Запрещается:
* Использовать `grid` для простого расположения двух элементов.
* Использовать сложный `flex` layout там, где `grid` очевидно проще.
* Создавать nested flex containers без необходимости.

---

# 5. Avoid Nested Layout Hell

Запрещается создавать большое количество вложенных layout-контейнеров.

### Плохой пример:
```text
flex
└── flex
    └── flex
        └── flex
            └── content
```

Если структура становится глубоко вложенной, необходимо остановиться и проверить архитектуру DOM.

### Возможные решения:
* убрать лишний wrapper;
* использовать `grid`;
* изменить структуру;
* использовать `gap`;
* использовать layout родительского элемента.

---

# 6. Gap Before Margin

При управлении расстоянием между элементами одного layout-контейнера необходимо в первую очередь использовать:

```css
gap
```

### Предпочтение:
```text
flex + gap
```
или:
```text
grid + gap
```
вместо большого количества индивидуальных:
```css
margin-bottom
margin-right
margin-left
```

Не использовать хаотичные margin для построения общей структуры.
`margin` использовать только для действительно локальных случаев (например, отталкивание единичного элемента).

---

# 7. Spacing Must Come From a System

Отступы не должны подбираться случайно.

### Запрещается:
```text
13px
17px
29px
37px
```
без причины.

Необходимо использовать последовательную spacing system:
* Tailwind default spacing scale (`p-1`, `p-2`, `p-3`, `p-4`, `p-6`, `p-8`, `p-12`, `p-16` и т.д.);
* Системный шаг: **4, 8, 12, 16, 24, 32, 48, 64**.

Главное требование: **Отступы должны быть системными и повторяемыми.**

---

# 8. No Positioning as Layout

Запрещается использовать `position: absolute` или `position: relative` в качестве основного инструмента построения layout.

`absolute positioning` разрешён только для:
* overlays (модальные окна, dropdown, tooltip);
* badges, если они действительно необходимы;
* floating controls;
* специально позиционируемых индикаторов.

Запрещается строить основную структуру страницы через:
```css
top
left
right
bottom
```

---

# 9. Responsive is Part of the Structure

Адаптивность нельзя добавлять в самом конце.

При создании layout необходимо сразу учитывать:
* mobile;
* tablet;
* desktop;
* большие экраны.

Каждая крупная структура должна проверяться на:
```text
Desktop
↓
Tablet
↓
Mobile
```

Нельзя просто пропорционально уменьшить desktop layout для mobile.
Необходимо определить:
* что меняет направление (row -> column);
* что скрывается;
* что переносится;
* что становится scrollable;
* что становится вертикальным.

---

# 10. Container Width Discipline

Контент не должен растягиваться на всю ширину экрана без необходимости.

Для каждой области определить:
* **Full-width**: backgrounds, application shells, dashboards, широкие таблицы.
* **Constrained** (например, `max-w-5xl`, `max-w-7xl`): обычные страницы, формы, лендинги, настройки.
* **Reading width** (например, `max-w-prose`, `max-w-2xl`): статьи, документация, длинный текст.

Ширина контейнера должна определяться содержимым и задачей, а не случайным значением.

---

# 11. No Random Max-Width

Запрещается случайно использовать `max-width: 1200px;` только потому, что это популярное число.

Каждый `max-width` должен соответствовать:
* типу страницы;
* объёму контента;
* читаемости;
* используемой сетке;
* структуре приложения.

---

# 12. Text Should Not Be Used as a Layout Tool

Запрещается использовать текст для исправления layout:
* добавлять лишние пробелы (`&nbsp;&nbsp;&nbsp;`);
* использовать переносы строк (`<br />`) ради позиционирования;
* добавлять пустой текст;
* использовать символы для выравнивания.

Layout обязан строиться через CSS.

---

# 13. No Empty Structural Elements

Запрещается создавать пустые элементы:
```html
<div></div>
```
для:
* создания отступа;
* искусственного пространства;
* разделения блоков.

Использовать: `gap`, `padding`, `margin` и правильную структуру layout.

---

# 14. Section Discipline

Каждая крупная область страницы должна иметь понятную структуру:

```text
Page
│
├── Header
│
├── Main
│   │
│   ├── Page Header
│   │
│   ├── Primary Content
│   │
│   └── Secondary Content
│
└── Footer
```

Запрещается создавать страницу как хаотичный набор блоков. Каждая крупная область должна иметь назначение, иерархию и семантическую привязку.

---

# 15. Page Header Discipline

Page Header должен содержать только необходимую информацию.

### Допустимо:
* Название страницы (`h1`).
* Краткое описание, если оно действительно необходимо.
* Контекстное действие (кнопка действия на странице), если необходимо.

### Запрещается автоматически добавлять:
* иконку перед заголовком;
* букву в контейнере;
* псевдологотип;
* badge;
* dot label;
* `ONLINE`;
* `SECURITY`;
* декоративную подпись;
* бессмысленный subtitle.

Page Header не должен искусственно усложняться.

---

# 16. Alignment is Not Decoration

Все элементы должны быть выстроены относительно понятной системы.

Необходимо избегать:
* случайных horizontal offsets;
* элементов, начинающихся с разных позиций без причины;
* случайных размеров;
* визуального смещения.

Перед завершением layout проверить:
```text
Есть ли общая ось выравнивания?
Понятно ли, почему элементы находятся именно в этих позициях?
Связаны ли отступы между собой?
Нет ли случайных визуальных смещений?
```

---

# 17. DOM Depth Check

Перед завершением компонента необходимо проверить глубину DOM.

Если компонент выглядит так:
```text
Component
└── div
    └── div
        └── div
            └── div
                └── div
                    └── Content
```
необходимо проверить возможность упрощения. Большая вложенность разрешается только при реальной технической необходимости.

---

# 18. Layout Before Component Extraction

Не нужно автоматически создавать отдельный компонент для каждого визуального блока.

Сначала определить:
* Это самостоятельная функциональная часть?
* Будет ли использоваться повторно?
* Имеет ли собственную логику?
* Улучшает ли выделение компонента структуру проекта?

Если нет — не создавать отдельный компонент. Запрещается дробить интерфейс на десятки файлов ради формальной модульности.

---

# 19. Visual Hierarchy Without Extra Wrappers

Перед созданием нового контейнера необходимо сначала попробовать использовать:
* `spacing` (whitespace);
* `typography` (шрифтовые контрасты);
* `grid` / `flex`;
* `semantic structure`;
* `background contrast` при необходимости.

Не создавать дополнительную обёртку только ради визуального разделения.

---

# 20. Layout Final Check

Перед сдачей интерфейса необходимо проверить:

```text
[ ] 1.  HTML-структура логична.
[ ] 2.  Используются подходящие semantic elements (header, main, section, nav и т.д.).
[ ] 3.  Нет div без причины.
[ ] 4.  Нет лишних wrappers.
[ ] 5.  Нет глубокой вложенности без необходимости (DOM Depth Check пройден).
[ ] 6.  Flex используется для одномерных layout.
[ ] 7.  Grid используется для двумерных layout.
[ ] 8.  Нет nested layout containers без необходимости.
[ ] 9.  Gap используется для системного расстояния между элементами.
[ ] 10. Отступы соответствуют единой spacing system (без хаотичных px).
[ ] 11. Positioning (absolute/relative) не используется для построения основного layout.
[ ] 12. Нет пустых элементов ради spacing.
[ ] 13. Layout адаптивен (Desktop, Tablet, Mobile).
[ ] 14. Mobile layout спроектирован отдельно, а не просто уменьшен.
[ ] 15. Контейнеры имеют обоснованную ширину (full-width, constrained, reading).
[ ] 16. Нет случайных max-width.
[ ] 17. Все элементы имеют понятную систему выравнивания.
[ ] 18. Page Header не содержит декоративного мусора (бейджей, псевдологотипов).
[ ] 19. DOM-структура проверена на возможность упрощения.
[ ] 20. Интерфейс можно упростить без потери функциональности.
```

---

# Финальный принцип

GO-BUILD обязан создавать интерфейс по цепочке:

```text
СМЫСЛ
↓
СТРУКТУРА
↓
SEMANTIC HTML
↓
LAYOUT
↓
RESPONSIVE
↓
STYLING
↓
FINAL SIMPLIFICATION
```

### Запрещён обратный подход:
```text
КРАСИВО ВЫГЛЯДИТ
↓
ДОБАВЛЯЕМ КОНТЕЙНЕРЫ
↓
ДОБАВЛЯЕМ ОБВОДКИ
↓
ИСПРАВЛЯЕМ CSS
↓
ДОБАВЛЯЕМ ЕЩЁ WRAPPER
```

**Правильная вёрстка начинается с правильной структуры.**  
**Если для реализации интерфейса постоянно требуются дополнительные wrappers — сначала необходимо проверить структуру, а не добавлять ещё один `div`.**
