# Rule Enforcement & Execution Discipline

## 1. Фундаментальный сдвиг: от деклараций к принудительному исполнению

Главная проблема традиционных сводов правил: они описывают **желаемое состояние** («код должен быть чистым», «не добавляй лишнего»), но не содержат **процедурного барьера**, физически останавливающего агента перед выполнением несанкционированного действия. В результате агент бросается писать код, вспоминая о правилах только во время финального аудита (когда лишние сущности уже сгенерированы).

**GO-BUILD v1.14.1 меняет парадигму:**
> **Сначала проверка применимых правил → фиксация Pre-Action Audit → выполнение действия → верификация.**  
> Любое мутирующее действие без предшествующего Pre-Action Audit считается невалидным нарушением стандарта.

## 2. Иерархия правил и порядок разрешения конфликтов (Rule Priority Hierarchy)

Все требования стандарта разделены на 4 строгих уровня приоритета. Порядок разрешения любых коллизий строго однозначен:

```text
P0 (ABSOLUTE)  >>>  P1 (MANDATORY)  >>>  P2 (CONDITIONAL)  >>>  P3 (GUIDANCE)
```

| Уровень | Обозначение | Описание | Исключения | Действие при нарушении |
|---|---|---|---|---|
| **P0** | **ABSOLUTE** | Законы нулевой терпимости. Границы безопасности, скоупа и визуальной чистоты. | Исключения **ЗАПРЕЩЕНЫ**. | Немедленный **STOP** и откат. |
| **P1** | **MANDATORY** | Обязательные инженерные и интерфейсные протоколы для любого действия. | Только по прямому явному требованию пользователя. | Блокировка действия до исправления. |
| **P2** | **CONDITIONAL** | Процедуры, активируемые строго при наступлении контекстного триггера (Task Sizing). | Активируются только при совпадении условий триггера. | Пропуск (отключение), если условие не наступило. |
| **P3** | **GUIDANCE** | Архитектурные рекомендации, эвристики читаемости и проверенные паттерны. | Рекомендательный характер. | Анализ компромиссов (tradeoffs). |

### Правила разрешения коллизий:
1. **P0 Scope Lock подавляет любые рекомендации по качеству**: Никакие общие принципы доступности (a11y), масштабируемости, гибкости или надёжности из Разделов 4 и 6 не могут самостоятельно расширять scope задачи или служить оправданием добавления не запрашивавшихся UI-элементов (модалок, тостов, лоадеров).
2. **Минимальность (P1-3) подавляет модульность (P1-10) для SURGICAL_TASK**: При точечной задаче код правится по месту. Запрещено выносить код в новый файл модуля только потому, что его потенциально можно вынести.
3. **Task Sizing (P2-1) имеет абсолютный приоритет над протоколами анализа**: Если задача классифицирована как `SURGICAL_TASK`, составление 16 блоков ТЗ и запуск субагентов категорически запрещены, независимо от любых других требований в тексте стандарта.

## 3. Scope Lock и критерий технической необходимости

Перед выполнением любой задачи агент фиксирует **Scope Lock** — четкое разграничение границ вмешательства.

```text
┌─────────────────────────────────────────────────────────────────┐
│                           SCOPE LOCK                            │
├────────────────────────────────┬────────────────────────────────┤
│ [REQUESTED]                    │ [PROTECTED]                    │
│ Что явно запросил пользователь │ Файлы, модули, legacy и стили, │
│ (единственная цель задачи).    │ которые нельзя ломать/менять.  │
├────────────────────────────────┼────────────────────────────────┤
│ [REQUIRED]                     │ [FORBIDDEN]                    │
│ Минимально необходимые шаги    │ Что категорически запрещено    │
│ для реализации [REQUESTED].    │ (отсебятина, бейджи, рефактор).│
└────────────────────────────────┴────────────────────────────────┘
```

### Защита от Scope Leakage: Критерий Strict Technical Necessity
Агенту категорически запрещено оправдывать добавление непрошенных сущностей ссылкой на «техническую необходимость» или «требования качества»:
* **В `[REQUIRED]` входит строго и исключительно:**
  1. *Синтаксические и типовые зависимости*: компиляция, типы TypeScript, обязательный импорт вызываемой функции, возврат ошибки;
  2. *Минимальная цепочка Data-Flow / State Wiring*: проброс пропса, вызов селектора стора/хука или минимальный API-запрос, без которых запрошенная функция физически не может получить или отобразить данные.
* **Категорически ЗАПРЕЩЕНО относить к `[REQUIRED]` (строго в `[FORBIDDEN]`):**
  * Модальные окна и диалоги подтверждения («А вдруг случайно нажмет?»);
  * Тост-уведомления и всплывающие плашки об успехе;
  * Внутренние лоадеры и спиннеры внутри кнопок;
  * Декоративные иконки и бейджи;
  * Дополнительное логирование и аналитику;
  * Fallback-сценарии для гипотетических сбоев.

## 4. Pre-Action Gate, Audit Stamp и Core-фильтры

Перед вызовом любого инструмента, изменяющего состояние кодовой базы (`write_to_file`, `replace_file_content`, мутирующий `run_command`), агент обязан зафиксировать **Pre-Action Audit Stamp** и пройти проверку по 5 бинарным условиям.

### Обязательный Pre-Action Audit Stamp
Во избежание скрытого обхода шлюза (Tool Call Ghost Bypass), перед каждым мутирующим вызовом инструмента агент обязан зафиксировать краткую строку аудита:
```text
[PRE-ACTION AUDIT]: Scope: OK | Rules: P0,P1 | Checks: PASS | Decision: PASS
```

### 5 бинарных проверок шлюза:
1. **Scope Check**: Действие лежит строго внутри `[REQUESTED]` / `[REQUIRED]` и не заходит в `[FORBIDDEN]`?
2. **Search Check**: Проверено ли отсутствие готовой реализации/функции/модуля в проекте (Search Before Create)?
3. **Core Checks (Anti-Slop & Layout)**: Пройдены ли экспресс-фильтры визуальной чистоты и вёрстки?
4. **Simplicity Test**: Это минимально достаточное прямое решение без абстракций-однодневок (Senior Simplicity)?
5. **Verify Ready**: Определен ли точный способ проверки результата шага (`Step → Verify`)?

### 3.1. Anti-Slop Core 6 (Экспресс-фильтр визуального мусора):
1. **[Zero-Emoji]**: В коде, разметке и текстах нет ни одного эмодзи.
2. **[No Corner Dots / Glow]**: Нет декоративных зеленых/серых точек в углах карточек или шапки.
3. **[No Header Badges / Pills]**: В Header нет бейджей версий (`v1.0`), тарифов (`Pro`), протоколов. Строго `Product Name Only`.
4. **[No Fake Context / Buzzwords]**: Нет выдуманных движков, режимов (`Bypass Ready`, `Ghost/Blatant`), маркетингового буллшита.
5. **[Border Last Principle]**: Нет Card-Hell (карточек в карточках) и рамок ради рамок; структура держится на отступах и типографике.
6. **[Status Must Have Consequences]**: Нет декоративных статусов процесса (`ONLINE`, `LIVE`, `IDLE SCAN`). Любой статус несет реальное функциональное последствие.

### 3.2. Layout Core 4 (Экспресс-фильтр архитектуры вёрстки):
1. **[Gap Before Margin]**: Расстояния между элементами внутри Flex/Grid регулируются строго через `gap`, а не через индивидуальные хаотичные margin.
2. **[Semantic First / No Div-Hell]**: Использование семантических тегов (`header`, `nav`, `main`, `section`, `button`) вместо бесконечных `div`-оберток без роли.
3. **[No Unnecessary Absolute Positioning]**: Запрет использования `position: absolute/relative` для построения основной структуры и потока страницы.
4. **[Responsive & Window Adaptivity]**: Запрет жестких пиксельных ширин контейнеров без `max-w-*`; обязательная адаптивность при сжатии окна.

> **БЛОКИРОВКА:** Если хотя бы на один вопрос ответ **НЕТ** — действие **БЛОКИРУЕТСЯ**. Агент обязан скорректировать решение до выполнения tool call.

## 5. Rule Trigger Map и Pre-Response Gate

### 5.1. Матрица триггеров действий с кодом:

| Намерение агента | Целевой инструмент | Применимые правила (P0 / P1 / P2) |
|---|---|---|
| **Правка существующего кода** | `replace_file_content` | • **P0-1** Scope Lock Integrity<br>• **P1-3** Surgical Changes & Anti-Style-Drift<br>• **P1-4** Clean Up Only Your Own Mess<br>• **P0-4** Защита чужого legacy-кода |
| **Создание нового файла / модуля** | `write_to_file` | • **P1-2** Search Before Create (поиск дубликатов)<br>• **P0-1** Scope Lock (просил ли пользователь файл?)<br>• **P1-1** Visual Purpose Gate (если UI-компонент)<br>• **P3-2** Senior Simplicity Test |
| **Верстка и оформление UI** | Разметка / стили / GUI | • **P0-2** Anti-Slop Core 6 & Layout Core 4<br>• **P1-6** Window-First Adaptivity & Content Priority<br>• **P1-7** Border Last & Spacing System |
| **Добавление зависимости** | `package.json`, `go.mod`... | • **P0-1** Scope Lock (требовалось ли явно?)<br>• **P1-2** Проверка stdlib и имеющихся пакетов<br>• **P2-3** Обязательный аудит через Libraries.dev |
| **Выполнение команд / Билд** | `run_command` | • **P0-3** Autonomous Execution (No Command Dumps)<br>• **P1-5** Step → Verify (команда проверки) |

### 5.2. Pre-Response Gate (Шлюз ответа пользователю):
Перед отправкой финального сообщения в чат агент обязан пройти 4 бинарных фильтра:
1. **Zero Command Dumps (P0-3)**: В сообщении НЕТ инструкций «пойдите в терминал и запустите X»? Команды выполнены агентом самостоятельно.
2. **Zero Log Dumps (P1-8)**: В сообщении НЕТ простыней сырых логов сборки или протоколирования каждого мелкого клика?
3. **Strict Language & Brevity (P1-8)**: Ответ сформулирован кратко, по сути, на чистом русском языке без шаблонных приветствий и формальностей?
4. **Verified Status**: В ответе зафиксирован реальный проверенный статус выполнения задачи?

## 6. Violation Protocol и Circuit Breaker

Если агент, субагент или тесты обнаруживают отклонение от правил:

```text
[ОБНАРУЖЕНИЕ НАРУШЕНИЯ]
        ↓
1. STOP: Немедленно остановить текущую цепочку правок.
        ↓
2. IDENTIFY: Назвать нарушенное правило (код P0/P1/P2) и строки в diff.
        ↓
3. REVERT / ISOLATE: Откатить несанкционированное изменение до чистого состояния.
        ↓
4. REPLAN: Скорректировать план строго в границах Scope Lock.
        ↓
5. FIX: Реализовать минимально необходимое решение без нарушения правил.
        ↓
6. VERIFY: Проверить устранение нарушения целевым тестом/линтером.
        ↓
7. PROCEED: Продолжить выполнение задачи только после валидации.
```

### Circuit Breaker (Предохранитель от бесконечного зацикливания и дрейфа скоупа):
* **Штатные исправления (не триггерят Circuit Breaker)**: До 3 микро-исправлений синтаксиса, пропущенных скобок, форматирования Prettier или ошибок линтера **в пределах исходно затронутого файла** являются нормальным рабочим процессом.
* **Триггеры аварийного срабатывания Circuit Breaker**:
  1. **Scope Drift**: Попытка агента перейти к редактированию других, не входящих в исходный Scope файлов для устранения ошибки;
  2. **Repeated Architectural Failure**: Повторение одной и той же фундаментальной логической ошибки 2 раза подряд;
  3. **Scope Deadlock**: Невозможность завершить задачу без расширения согласованного Scope Lock;
  4. **Repeated Violation**: Повторное нарушение одного и того же правила P0 или P1 в цикле правок.
* **Действия при срабатывании Circuit Breaker**:
  1. `FULL STOP`: Немедленная остановка любых изменений;
  2. `CLEAN REVERT`: Откат изменений до чистого базового состояния;
  3. `REPORT & ASK`: Кратко сообщить пользователю суть проблемы, возникший конфликт и запросить решение.

## 7. Continuous Compliance Check (Непрерывный аудит)

Вместо единственной проверки в самом конце разработки, комплаенс-аудит встроен в каждый шаг выполнения:

1. **Pre-Step Check**: Проверка намерения по Rule Trigger Map и фиксация Pre-Action Audit Stamp.
2. **Post-Step Micro-Audit**: Сразу после выполнения шага проверяется diff:
   * Не добавлены ли не запрашивавшиеся сущности?
   * Нет ли нарушений Anti-Slop Core 6 и Layout Core 4?
   * Не задет ли стиль соседних строк?
   * Удален ли временный отладочный код?
3. **Transition**: Переход к следующему шагу разрешен только при чистом Micro-Audit.

## 8. Оцифрованная матрица Task Sizing

Масштаб процессов определяется строгими оцифрованными критериями. **Task Sizing имеет высшую силу над любыми устаревшими протоколами анализа в тексте стандарта.**

| Класс задачи | Оцифрованные критерии | Обязательный протокол | Запрещенные действия |
|---|---|---|---|
| **SURGICAL_TASK** *(Micro-Fix / Local Feature / Mechanical Refactor)* | • 1–2 затронутых файла (diff ≤ 50 строк)<br>• **ИЛИ** механические шаблонные правки (Mechanical Repetitive Changes) по любому числу файлов (переименование импорта, замена константы, смена версии API с diff ≤ 3–5 строк на файл) | • Экспресс Scope Lock<br>• 1 ведущий агент<br>• Pre-Action Audit перед каждой правкой<br>• Приоритет P1-3 (правка по месту) над вынесением в модуль | • **СТРОГО ЗАПРЕЩЕНО** составлять 16 блоков ТЗ.<br>• **СТРОГО ЗАПРЕЩЕНО** привлекать субагентов.<br>• **СТРОГО ЗАПРЕЩЕНО** добавлять новые библиотеки. |
| **MAJOR_FEATURE** *(Изолированная подсистема / Экран)* | • 3–8 затронутых файлов<br>• 1 новый изолированный экран / компонент / модуль<br>• Локальная миграция данных | • Сокращенный анализ архитектуры (блоки 1, 6, 7, 11, 12 шаблона)<br>• 2–4 профильных субагента (Architect, Frontend, Backend, QA) | • **ЗАПРЕЩЕНО** переписывать глобальную архитектуру ядра.<br>• **ЗАПРЕЩЕНО** запускать > 4 субагентов. |
| **FULL_PROJECT** *(Проект с нуля / Новая архитектура)* | • > 8 файлов (не механических)<br>• Создание проекта с нуля<br>• Полная смена стека/архитектуры<br>• Мультисервисная система | • **Обязательный полный 16-блочный анализ ТЗ (P2-1)**<br>• Оркестрация команды из 4–10 субагентов<br>• Полный фазовый цикл от ТЗ до QA | • **СТРОГО ЗАПРЕЩЕНО** начинать разработку без утвержденного 16-блочного анализа. |
