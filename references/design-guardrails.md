# GO-BUILD: Жёсткие визуальные запреты и Anti-AI-Slop

## Главный принцип

Интерфейс не должен содержать элементы, которые существуют только ради создания впечатления современного, технологичного или премиального дизайна.

Каждый визуальный элемент должен отвечать на вопрос:

**Зачем пользователь должен это видеть?**

Если у элемента нет понятной функциональной, информационной или навигационной цели — его необходимо удалить.

Запрещается создавать интерфейс по шаблонам, характерным для автоматически сгенерированного AI-дизайна.

---

## 1. Zero-Emoji — Абсолютный запрет

Использование эмодзи в интерфейсе категорически запрещено.

Запрещается использовать эмодзи:
* в кнопках;
* в заголовках;
* в карточках;
* в уведомлениях;
* в статусах;
* в меню;
* в sidebar;
* в пустых состояниях (empty states);
* в onboarding;
* в описаниях;
* в декоративных элементах.

Нельзя заменять нормальные интерфейсные иконки эмодзи.

### Категорически запрещено:
```text
[ЗАПРЕЩЕНО]:
🚀 Быстрый старт
🔥 Популярное
✨ Новые возможности
🔒 Безопасность
📊 Аналитика
```

Если необходима иконка, использовать полноценную SVG-иконку из разрешённых библиотек.

### Приоритет библиотек:
1. **Lucide React** ([lucide.dev](https://lucide.dev/guide/react/))
2. **Hugeicons** ([hugeicons.com](https://hugeicons.com/))
3. Другие подходящие библиотеки из утверждённого набора ([shadcn/ui Icons](https://www.shadcn.io/icons/libraries)).

Эмодзи допускаются только если пользователь напрямую потребовал их использование. Во всех остальных случаях: **ZERO EMOJI**.

---

## 2. Anti-AI-Slop

GO-BUILD категорически запрещается автоматически использовать распространённые AI-шаблоны интерфейсов.

Необходимо избегать дизайна, который выглядит так, будто он был создан генератором без понимания конкретного продукта.

### Запрещается автоматически создавать:
* бессмысленные бейджи;
* маркетинговые подписи;
* декоративные статусы;
* псевдотехнические индикаторы;
* лишние точки перед текстом;
* случайные иконки;
* декоративные контейнеры;
* чрезмерное количество карточек;
* визуальные элементы без функции;
* одинаковые блоки ради заполнения страницы;
* бессмысленные показатели;
* искусственные статусы;
* fake activity;
* fake metrics.

Интерфейс должен строиться вокруг реального продукта и реальных действий пользователя, а не вокруг визуальных паттернов.

---

## 3. Запрет на Dot Labels и точки перед текстом (GREEN DOT ≠ GOOD DESIGN)

Категорически запрещается автоматически создавать текстовые элементы с точкой, индикатором или маленьким кружком перед текстом, если этот элемент не отображает реальное состояние системы.

Зелёная (или любая цветная) точка запрещена как декоративный элемент. Нельзя автоматически создавать:
```text
● ONLINE
● ACTIVE
● READY
● IDLE
```
только для создания ощущения работающей системы.

### Запрещённые примеры:
```text
● ONLINE
● ACTIVE
● READY
● IDLE
● SECURITY
● SYSTEM ACTIVE
● SECURE PLATFORM
● LIVE
● AVAILABLE NOW
• ONLINE
○ SECURITY
● VERIFIED
```

Подобные элементы нельзя использовать:
* над заголовками;
* рядом с заголовками;
* внутри hero-блоков;
* внутри карточек;
* в декоративных контейнерах;
* для создания «технологичного» внешнего вида.

### Когда Dot Indicator разрешён (4 обязательных критерия):
Индикатор разрешён исключительно если одновременно выполняются условия:
1. **Статус является реальным** (получает реальные данные из системы, а не захардкожен);
2. **Он динамически меняется** во время работы продукта;
3. **Изменение статуса имеет значение** для пользователя;
4. **Пользователь должен видеть этот статус** для совершения действий.

Пример допустимого использования:
```text
● Сервер доступен
```
*Но только если сервер действительно опрашивается и его статус является реальными данными. Запрещается имитировать статус.*

## 4. Запрет на бессмысленные Security Labels

Нельзя выводить пользователю слова:
* `Security`
* `Secure`
* `Protected`
* `Verified`
* `Encrypted`
* `Privacy First`

если эта информация не нужна пользователю в текущем контексте. Запрещается использовать безопасность как декоративный элемент интерфейса.

### Плохой пример:
```text
SECURITY

Ваш аккаунт под защитой
```
*(если пользователь просто находится на обычной странице приложения и эта информация не требует его действий)*.

Безопасность должна работать в системе, а не постоянно рекламироваться пользователю.

### Информация о безопасности должна отображаться только когда:
* пользователь совершает действие, связанное с безопасностью;
* требуется подтверждение прав или двухфакторная аутентификация;
* существует реальное предупреждение системы;
* пользователь должен принять решение;
* статус безопасности действительно важен в текущем контексте.

Главный вопрос: **Нужно ли пользователю видеть это именно сейчас?** Если нет — элемент не создаётся.

## 5. Запрет на бессмысленные маркетинговые тексты

Категорически запрещается автоматически добавлять тексты вроде:
```text
BUILT FOR THE FUTURE
THE NEXT GENERATION
POWERFUL. FAST. SECURE.
PREMIUM EXPERIENCE
SMART SOLUTIONS
ALL-IN-ONE PLATFORM
ALL-IN-ONE
TOP PERFORMANCE
ULTRA PERFORMANCE
SEAMLESS EXPERIENCE
```
если они не являются реальной частью утверждённого контента продукта.

Запрещается использовать абстрактные маркетинговые фразы для заполнения пространства. Каждый текст должен передавать конкретную информацию.

## 6. Запрет на декоративные контейнеры

Контейнер нельзя создавать только потому, что визуально кажется, что «здесь чего-то не хватает». Каждый контейнер должен иметь причину существования.

### Контейнер разрешён, если он:
* объединяет связанную информацию;
* разделяет разные функциональные области;
* создаёт необходимую визуальную иерархию;
* является интерактивным элементом;
* требует визуального отделения для понимания интерфейса.

### Контейнер запрещён, если он:
* содержит один короткий текст без необходимости;
* существует исключительно ради обводки;
* используется как декоративная рамка;
* вложен в другой контейнер без функциональной причины;
* создаёт искусственную карточность интерфейса.

---

## 7. Запрет на Card-Hell

Запрещается превращать весь интерфейс в набор отдельных карточек.

### Запрещённая структура:
```text
Page
 └── Card
      └── Card
           └── Card
```
без функциональной необходимости.

Если несколько элементов являются частью одного логического пространства, они не обязаны находиться в отдельных контейнерах.

### Предпочтение отдаётся:
* визуальной иерархии;
* отступам (whitespace, gap);
* типографике;
* сетке;
* разделению пространства.

Необходимо сначала попытаться решить задачу без дополнительной рамки.

---

## 8. Border Last Principle (Принцип последней очереди для обводки)

Обводка не должна быть стандартным способом разделения интерфейса.

Перед добавлением border необходимо проверить:

**Можно ли создать понятную структуру без обводки?**

Если да — обводка не используется.

### Разрешается использовать:
* spacing (отступы);
* typography (размер, начертание, иерархия);
* background contrast (контраст фоновых поверхностей);
* layout (сетка и выравнивание);
* hierarchy (логический порядок).

Обводка используется только тогда, когда она действительно помогает восприятию.

### Запрещается:
* обводить каждый блок;
* обводить каждую карточку;
* создавать несколько вложенных рамок;
* использовать border как основной стиль интерфейса.

---

## 9. Запрет на Decorative Status & Fake Technical Aesthetic

Запрещается создавать ощущение «технологичности» через случайный технический текст и статусы, которые не связаны с реальным состоянием системы.

### Запрещённые примеры псевдотехнической эстетики:
```text
IDLE SCAN
SYSTEM READY
PROCESSING
CORE ACTIVE
NETWORK SECURE
ENGINE ACTIVE
CORE READY
SESSION LIVE
SYSTEM ONLINE
ALL SYSTEMS ACTIVE
SECURE CONNECTION
AI READY
LIVE PLATFORM
```
если эти процессы:
* не существуют в реальности;
* не отображают реальные данные;
* не требуют внимания пользователя.

**Технический текст не является дизайном.**

### STATUS MUST HAVE CONSEQUENCES (Статус обязан иметь последствия)
Любой статус обязан отвечать на вопрос:
> **Что изменится для пользователя, если этот статус изменится?**

Например:
```text
● IDLE SCAN
```
Если статус изменится с `IDLE` на что-то другое, но пользователь:
* ничего не должен делать;
* ничего не получает;
* интерфейс никак не меняется;

то этот статус **не должен существовать в интерфейсе**.

* **Никаких fake status.**
* **Никаких fake metrics.**
* **Никаких fake activity indicators.**
* **Никакой выдуманной технической эстетики.**

## 10. Запрет на бессмысленные цифры

Запрещается добавлять статистику ради заполнения интерфейса.

### Запрещённые примеры:
```text
99.9% Reliability
10K+ Users
24/7 Support
100% Secure
```
если эти данные:
* не являются реальными;
* не предоставлены пользователем;
* не загружаются из системы;
* не имеют конкретного смысла.

Любые цифры должны быть:
* **реальными;**
* **проверяемыми;**
* **контекстно необходимыми.**

---

## 11. Запрет на декоративные иконки

Иконка не должна появляться автоматически рядом с каждым текстом.

Иконки используются только когда:
* ускоряют понимание;
* обозначают действие (кнопки с понятной семантикой);
* помогают навигации;
* отображают реальное состояние;
* имеют функциональное значение.

Запрещается конструкция:
```text
[ICON] Заголовок
```
только потому, что заголовок визуально кажется пустым.

---

## 12. Запрет на бейджи над заголовками (No Pre-Header Badges)

Категорически запрещается создавать декоративные тексты, бейджи или подписи над основными заголовками.

### Запрещённый пример:
```text
[ PRODUCT MANAGEMENT ]

# Управляйте своим бизнесом
```

Также запрещены конструкции:
```text
[ NEW ]
[ PLATFORM ]
[ DASHBOARD ]
```
расположенные исключительно как декоративный элемент над главным заголовком.

Основной заголовок должен начинать визуальный блок самостоятельно, если дополнительный контекст не является функционально необходимым.

---

## 13. Запрет на логотипообразные контейнеры перед заголовком

В header или верхней части основного контейнера категорически запрещается автоматически создавать декоративные контейнеры с:
* иконкой;
* буквой;
* сокращением;
* аббревиатурой;
* псевдологотипом.

### Запрещённые примеры:
```text
[ A ]  Analytics Dashboard
```
или:
```text
[ Icon ]  Welcome back
```

Подобные элементы допускаются только если они являются:
* реальным логотипом проекта;
* функциональной кнопкой;
* необходимой частью интерфейса.

Нельзя создавать такие элементы автоматически ради дизайна.

## 14. Правила Header, Radical Header Minimalism & Purity Formula

Header (верхний блок) должен быть:
* минимальным;
* функциональным;
* логичным.

### ПОЖИЗНЕННЫЕ ЗАПРЕТЫ В ШАПКЕ И ДИЗАЙНЕ:

1. **❌ Зелёная точка / индикатор слева сверху (Top-Left Status Dot Ban)**:
   * Категорический пожизненный запрет на размещение цветных (зелёных, жёлтых, серых, синих) точек, кружков, светодиодов в левом верхнем углу, перед заголовком или в верхнем баре (`●`, `○`, `•`).
   * Точка слева сверху запрещена как рудимент AI-slop, создающий фальшивое ощущение статуса или терминальной эстетики. Индикация реального рабочего статуса выносится в функциональное тело интерфейса, а не в угол шапки.

2. **❌ Лишние бейджи в шапке (`Pro`, `WireGuard`, тарифы, протоколы)**:
   * Категорический запрет на размещение в Header бейджей тарифных планов (`Pro`, `Premium`, `Free`, `Plus`), чипов протоколов (`WireGuard`, `OpenVPN`, `VLESS`, `Shadowsocks`), статусов аккаунта и любых декоративных пилюль (pills/badges).
   * Шапка — это не рекламный щит и не витрина протоколов. Если протокол или тариф настраивается — он выбирается в настройках или отдельном селекторе, а не висит украшением возле логотипа.

3. **❌ Перегруженный верхний блок (No Overloaded Top Block)**:
   * Запрещено нагромождать в верхнем блоке несколько сущностей одновременно (логотип + бейдж + протокол + статус + кнопка профиля + уведомления).
   * Верхний блок содержит только чистое название продукта либо остаётся пустым (в утилитах и десктопных окнах).

4. **❌ Декоративные элементы без функции (Запрет элементов «для красоты»)**:
   * Запрещено добавлять любые элементы интерфейса просто «для красоты», для симметрии или «чтобы экран не казался пустым».
   * Каждый элемент обязан нести конкретную, проверяемую пользовательскую функцию (прямое действие либо критически важная информация).
   * Если элемент нельзя нажать и его отсутствие не ломает понимание данных — **он немедленно удаляется**.

5. **PRODUCT NAME ONLY (Только название продукта)**:
   В Header по умолчанию находится только то, что необходимо.
   Если приложение называется:
   ```text
   ASCII EYE
   ```
   то агент не имеет права превращать это в:
   ```text
   ASCII EYE // V1.0
   ● IDLE SCAN
   ```
   без прямой просьбы пользователя и без функциональной причины. Вопрос: *«Нужна ли эта информация пользователю прямо сейчас?»* — Если нет: **Удалить.**

6. **VERSION INFORMATION IS NOT DECORATION (Версия — не украшение)**:
   Запрещается автоматически писать `// V1.0` или `VERSION 1.0` рядом с названием продукта. Версия допустима только если: (1) важна пользователю, (2) это DevTool/CLI, (3) в системном разделе About, (4) нужна для поддержки, (5) напрямую запрошена.

### 🎯 PURITY FORMULA: ПРИНЦИП МАКСИМАЛЬНОЙ ЧИСТОТЫ

Интерфейс цифрового продукта или утилиты обязан быть предельно чистым и строиться по строгой формуле:

> **Название Продукта + Основная кнопка действия + Реальный статус + Ключевая метрика + Селектор/Ввод**

#### Эталонный пример (VPN / Utility Interface):
```text
VPN + основная кнопка + статус + скорость + сервер
```

Ровно 5 смысловых узлов, решающих 100% пользовательской задачи:
1. **Название продукта** (чистое, без точек, бейджей `Pro` и версий);
2. **Основная кнопка** (главное действие: подключить/запустить/конвертировать);
3. **Реальный статус** (чёткое текстовое состояние: Подключено / Отключено / В процессе);
4. **Ключевая метрика** (скорость, пинг, трафик или время сессии — только реальные цифры);
5. **Селектор / Сервер** (выбор целевой локации, сервера или режима без декоративного мусора).

Всё остальное — лишний когнитивный шум, подлежащий беспощадному удалению.

## 15. NO FAKE PRODUCT CONTEXT (Жёсткий запрет на выдуманный контекст)

GO-BUILD категорически запрещено самостоятельно добавлять в интерфейс:
* версии;
* build information;
* номера релизов;
* названия внутренних систем;
* fake system names;
* технические статусы;
* режимы работы;
* scanner labels;
* process labels;
* debug-информацию;
* названия движков;
* бессмысленные идентификаторы.

Если пользователь не попросил это явно и информация не нужна для работы продукта — **она не создаётся**.

### Запрещённые примеры:
```text
PRODUCT // V1.0

SYSTEM V2.4

BUILD 2026.09

IDLE SCAN

ENGINE ACTIVE

CORE READY

SESSION LIVE

SYSTEM ONLINE
```

## 16. NO FAKE BUILD IDENTITY

GO-BUILD запрещено самостоятельно придумывать продукту:
* версию;
* build;
* codename;
* engine;
* system mode;
* protocol;
* scanner;
* AI mode;
* internal state.

### Плохие AI-паттерны (категорически запрещены):
```text
APP NAME // V1.0
```
```text
PROJECT_X / BUILD_01
```
```text
NEURAL ENGINE
```
```text
SYSTEM INTERFACE
```
```text
AI POWERED TERMINAL
```
если это не является частью реального продукта, утверждённого пользователем.

---

## 17. NO INVENTED UI STORYTELLING (Запрет на выдуманный нарратив)

GO-BUILD запрещено придумывать продукту дополнительный сценарий ради атмосферы.

Например, пользователь попросил:
> *«Сделать просмотр изображения в ASCII.»*

Агент не имеет права самостоятельно придумывать:
```text
ASCII EYE

IDLE SCAN

FIT 90%

INVERT

GAZE X

PUPIL DILATION

FPS 121
```
если пользователь просил просто приложение для просмотра или обработки изображения.

**Продукт делает только то, что необходимо его задаче.**
Не нужно создавать «историю системы» и выдуманный лор вокруг обычной функции.

---

## 18. INFORMATION MUST EARN ITS PLACE & THE "WHY WOULD USER CARE?" TEST

Каждый текст должен **заслужить своё место в интерфейсе**.

### Чек-лист проверки текста (5 вопросов):
Перед добавлением любого текста агент обязан проверить:
```text
1. Откуда появилась эта информация?
2. Реальна ли она?
3. Нужна ли она пользователю?
4. Что пользователь сделает благодаря этой информации?
5. Что произойдёт, если её удалить?
```
Если ответ на 5-й вопрос:
```text
Ничего.
```
**Текст немедленно удаляется.**

### THE "WHY WOULD USER CARE?" TEST
Перед добавлением любой технической информации агент обязан задать вопрос:
> **Почему пользователю вообще должно быть не всё равно на эту информацию?**

Если нет конкретного, практического ответа — **информация не показывается**.

---

## 19. USER REQUEST > AI ATMOSPHERE (Фундаментальный принцип)

GO-BUILD никогда не должен добавлять:
* атмосферу;
* fake-tech эстетику;
* терминальный стиль;
* системные подписи;
* версии;
* статусы;
* технический жаргон;

**если пользователь этого не просил и это не требуется функционально.**

> **Не придумывай продукту личность, систему или процессы, которых в задаче не существует.**

---

## 20. Запрет на Cringe Buzzwords, Fake Presets & Pseudo-Hacker Slop (NO CHEESY OPTIONS & FAKE MODES)

Категорически запрещается использовать инфантильные псевдохакерские ярлыки, мерзкие штампы из сомнительного софта и выдуманные бинарные опции (fake 2-option presets).

### 1. Запрет на псевдохакерский/эксплойт-жаргон:
Категорически запрещены термины:
```text
Bypass Ready
Fast Injection
Kernel Inject
Stealth Inject
Memory Bypass
Hook Ready
Payload Active
Anti-Detection Ready
```
Если создаётся системная утилита, загрузчик, компилятор или интеграционный сервис — все этапы и статусы должны называться строго профессиональным инженерным языком:
* `Готов к работе` (вместо `Bypass Ready`);
* `Загрузка модуля` / `Подключение` (вместо `Fast Injection`);
* `Компиляция` / `Сборка`;
* `Статус: Активен`.

### 2. Запрет на мерзкие бинарные пресеты (No Cheesy 2-Option Presets):
Категорически запрещены дурацкие шаблонные названия пар опций в стиле дешевых чит-меню:
```text
Ghost & Blatant
Legit vs Rage
Stealth vs Aggressive
Silent vs Loud
```
Запрещено искусственно навязывать пользователю бинарный выбор («2 options») с пафосными эпитетами ради видимости функционала.

Все опции и переключатели обязаны отражать **реальные технические параметры**:
* Конкретный протокол: `TCP / UDP`, `IPv4 / IPv6`, `WireGuard / Shadowsocks`;
* Реальный режим обработки: `Стандартный / Расширенный`, `Строгий / Мягкий`;
* Точные числовые параметры: задержка (мс), размер буфера (КБ), количество потоков.

### 3. Запрет на гиперболический performance-буллшит:
Запрещены пустые хвалебные слова в названиях опций, переключателей и бейджей:
```text
Top Performance
Ultra Performance
Maximum Speed
Turbo Boost
Hyper Speed
Extreme Power
Fast Mode
```
Если есть режим оптимизации — он формулируется через конкретный технический эффект: `Энергосбережение`, `Аппаратное ускорение`, `Многопоточный рендеринг (8 потоков)`. Без рекламной шелухи.

### 4. Запрет на зонтичные маркетинговые штампы:
Запрещены клише-названия:
```text
All-in-One
Ultimate Suite
Complete Solution
Full Pack
```
Опции должны называть вещи своими именами: `Полная установка`, `Базовый комплект`, либо содержать конкретный список модулей.

## 21. Правило трёх действий

Интерфейс должен стремиться к максимальной простоте.
Основной пользовательский сценарий должен быть максимально коротким:

```text
1. Пользователь зашёл.
       ↓
2. Пользователь выбрал.
       ↓
3. Пользователь получил результат.
```

Если пользователь вынужден долго разбираться, куда нажимать и как работает интерфейс, значит интерфейс требует упрощения.

Интерфейс должен объяснять себя через:
* расположение элементов;
* понятные названия;
* последовательность действий;
* визуальную иерархию.

---

## 22. Проверка каждого элемента (5 контрольных вопросов)

Перед добавлением любого визуального элемента GO-BUILD обязан проверить:

1. **Есть ли у него функция?**  
   *Если нет — удалить.*
2. **Передаёт ли он пользователю необходимую информацию?**  
   *Если нет — удалить.*
3. **Помогает ли он совершить действие?**  
   *Если нет — удалить.*
4. **Можно ли убрать его без ухудшения интерфейса?**  
   *Если да — удалить.*
5. **Создан ли он только для визуального эффекта?**  
   *Если да — удалить.*

## 23. Anti-AI-Slop Final Check (25 обязательных пунктов)

Перед завершением frontend-разработки необходимо провести обязательную финальную проверку интерфейса:

```text
[ ] 1.  Нет эмодзи ни в одном компоненте, кнопке, меню или тексте.
[ ] 2.  Нет бессмысленных dot labels и декоративных точек перед текстом (● ONLINE, ● IDLE).
[ ] 3.  Категорически нет точки/индикатора слева сверху в шапке (Top-Left Status Dot).
[ ] 4.  Зелёная точка не используется как украшение; индикаторы присутствуют только при соблюдении 4 критериев (реальный, динамический, значимый, необходимый).
[ ] 5.  Нет текстов вида ONLINE / SECURITY / LIVE ради псевдотехнической эстетики.
[ ] 6.  Нет fake status и искусственных индикаторов процессов (IDLE SCAN, CORE ACTIVE).
[ ] 7.  Любой статус имеет последствия для пользователя (Status Must Have Consequences).
[ ] 8.  Нет fake metrics и выдуманных цифр статистики (99.9%, 10K+).
[ ] 9.  Нет бейджей тарифов (Pro, Premium) и протоколов (WireGuard, OpenVPN) в шапке.
[ ] 10. Верхний блок не перегружен: соблюден Radical Header Minimalism (только имя или пустое место).
[ ] 11. Нет бейджей и надзаголовочных плашек над H1/H2 ([ DASHBOARD ]).
[ ] 12. Нет псевдологотипов и иконок-в-квадратах перед заголовками ([ A ]).
[ ] 13. В Header строго соблюден принцип Product Name Only: нет выдуманных версий (// V1.0), билдов и декоративных статусов.
[ ] 14. Версия продукта не выведена как декорация и присутствует только если функционально оправдана (About, DevTool, поддержка).
[ ] 15. Нет выдуманного контекста продукта (No Fake Product Context: версии, кодовые имена, названия движков, фейковые режимы).
[ ] 16. Нет навязанного нарратива и псевдосистемной атмосферы (No Invented UI Storytelling: User Request > AI Atmosphere).
[ ] 17. Каждый текст заслужил свое место (Information Must Earn Its Place, пройден тест «Why Would User Care?»).
[ ] 18. Нет ни одного элемента «для красоты» без конкретной функции.
[ ] 19. Нет контейнеров без функции и рамок ради рамок.
[ ] 20. Нет «Card-Hell» (избыточной вложенности карточек в карточки).
[ ] 21. Соблюден принцип Border Last: структура построена на отступах и типографике.
[ ] 22. Интерфейс утилиты следует Purity Formula: Название + Основная кнопка + Статус + Скорость/Метрика + Сервер/Селектор.
[ ] 23. Нет псевдохакерских и эксплойт-ярлыков (Bypass Ready, Fast Injection, Kernel Inject).
[ ] 24. Нет инфантильных бинарных пресетов и мерзких названий опций (Ghost & Blatant, Legit vs Rage).
[ ] 25. Нет гиперболического performance-буллшита (Top Performance, Ultra Speed) и зонтичных штампов (All-in-One).
```

## Главное правило

GO-BUILD не должен спрашивать:

**Что ещё можно добавить, чтобы интерфейс выглядел интереснее?**

GO-BUILD обязан спрашивать:

**Что можно убрать, чтобы интерфейс стал понятнее и лучше?**

Если элемент не выполняет конкретную функцию — он не нужен.
